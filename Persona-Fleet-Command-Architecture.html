Architecture proposal

Persona Fleet Command on React, Azure and Microsoft Fabric

How the prototype becomes a production app: a React front end on Azure Static Web Apps, a TypeScript API on Azure Functions, and Microsoft Fabric for both analytics and writeback.

Status Draft for reviewDate 17 Sep 2026Source personalfleet.html prototype

01Recommended stack

One choice per layer. The stripe colours match the layers in the diagrams below.

Frontend
React 19 + TypeScript + Vite, hosted on Azure Static Web Apps (Standard)
API / middleware
An API written for this front end on Azure Functions (Flex Consumption, Node 20, TypeScript), attached as the Static Web App's linked backend. Add Azure API Management only if other teams need the API.
Caching & async
Azure Managed Redis for read caching. Azure Service Bus + Durable Functions for multi-step writes such as a persona switch.
Reads
Fabric Warehouse (or the Lakehouse SQL analytics endpoint) with a gold layer shaped for each screen.
Writeback
SQL database in Fabric for baselines, persona changes, exceptions and the audit log. It copies itself to OneLake automatically, so analytics sees writes almost immediately.
Ingestion
Fabric Data Factory pipelines and Copy jobs, Spark notebooks, medallion Lakehouse (bronze → silver → gold).
Identity
Microsoft Entra ID through Static Web Apps sign-in. The API reaches Fabric with a managed identity. Secrets live in Key Vault.
Delivery
Application Insights, Bicep via azd, GitHub Actions, Fabric Git integration and deployment pipelines.

Why put an API between React and Fabric

Writes fan outSwitch, "Raise provisioning request" and baseline edits touch Fabric, ServiceNow, Intune and Entra.
Data volumeMapping confidence alone covers about 12,000 title rows. Aggregation belongs on the server.
SecuritySecrets and role checks stay out of the browser.
Why TypeScript, not .NET, for the API. The scoring logic from the prototype (scoreDevice, buildModel, fitClass) becomes one shared package. The browser uses it for the live what-if sliders and the API uses the same code, so the numbers always agree.

Persona switch, end to end

The one flow that crosses every system. It runs as a Durable Functions orchestration so each step can retry or be compensated, replacing the prototype's hand-written undo in xApplySwitch.

Patterns

  • Caching: Redis cache-aside on reads, time-to-live matched to the gold refresh (for example 15 minutes), keys cleared when a baseline is published.
  • Idempotency: writes accept an Idempotency-Key header.
  • Authorisation: read x-ms-client-principal, check roles, record the user in audit_log.
  • API Management (optional): add Basic v2 or Standard v2 when outside consumers such as a ServiceNow widget or Power Automate need the API.

Alternatives considered

OptionWhy not the primary path
Fabric API for GraphQL, called from the SPAWorkable for read-only dashboards, but weak for aggregation-heavy screens and for coordinating ServiceNow, Graph and Intune.
Fabric User Data FunctionsFine for simple writeback; this app needs async orchestration across several systems.
Power BI EmbeddedLoses the custom D3 experience. Keep it for ad-hoc analysis.

Gold model

  • dim_persona, dim_app_catalog, dim_date
  • device_scored: pillar scores, fit_class, under_prov
  • fact_device_telemetry_daily: drives the 12-week health trend
  • fact_ticket: with type, sla_breached, week
  • job_title_mapping: conf and why
  • fact_persona_migration, fact_app_exception
  • Views: vw_persona_health, vw_fit_by_persona, vw_ticket_health

Notebooks

  • Scoring: a Python port of the shared scoring logic, run against the published baseline, with a parity test against the TypeScript package using the same fixtures.
  • Title → persona mapping: rules plus a classifier (scikit-learn, or Azure OpenAI embeddings with a similarity score). Outputs the confidence and the "why flagged" reason; review-queue decisions feed back as labels.

SQL database tables

  • baseline: persona, version, Draft / Published, values, edited by, edited at
  • persona_change: user, from, to, status, orchestration id, requested by
  • mapping_override: title, department, persona, reviewer
  • app_exception (local copy of RITM state) and audit_log

Scheduling: one orchestrating pipeline runs ingest → silver → scoring → Warehouse refresh. Publishing a baseline triggers a re-score through the Fabric REST API.

06Security and networking

AreaControls
IdentityUsers sign in with Entra ID; roles are Entra app roles. The Functions managed identity gets Contributor on the Fabric workspace, or item-level Read / ReadData on the Warehouse and Write on the SQL database. A Fabric admin enables Service principals can use Fabric APIs, scoped to a security group.
Least privilegeSeparate read and write identities if required. Graph GroupMember.ReadWrite.All limited to persona groups through a custom role or administrative unit. ServiceNow integration user holds scoped Table API roles only.
NetworkOptional Static Web App private endpoint. Functions VNet integration with private endpoints for Key Vault, Redis and Service Bus. Fabric workspace-level Private Link where policy requires it.
Data protectionNames and emails stay in gold under Warehouse column-level security. The API masks email for Viewer-only roles.
ApplicationCSP, Zod validation on every input, parameterised SQL only.

09Open decisions

These shape the design and are worth settling before phase 1 ends.

Telemetry sourceEndpoint Analytics or a third-party tool for boot time, crashes and battery. Decides the ingestion design.
Where persona membership livesEntra groups (recommended, so Intune follows) or a field in the HR system.
Row-level visibilityIf managers only see their own org: filter in the API (recommended) or use delegated access to Fabric, which needs MSAL in the SPA.
Other API consumersIf anything besides this front end will call the API, add API Management from day one.
